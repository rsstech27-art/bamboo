# Зоны в рабочей и релизной версиях

Проект остаётся единым. Каталог и список релизных зон находятся в `src/lib/zones.ts`.

- Рабочий сервер (`pnpm --filter @workspace/bamboo-studio run dev`): все шесть зон, оконный и дверной проёмы помечены «В разработке».
- Релизная сборка (`pnpm --filter @workspace/bamboo-studio run build`): только стена, стена с выступом, ТВ-зона и колонна.
- Просмотр готовой сборки: `pnpm --filter @workspace/bamboo-studio run serve`. Команды Vite требуют настроенных `PORT` и `BASE_PATH`, как и существующий сервер приложения.

Доступность определяется Vite `import.meta.env.DEV` при сборке. URL, локальное хранилище и вход менеджера не включают скрытые зоны в релизе. Режим `vite build --mode development` тоже является сборкой, а не рабочим сервером: он не предназначен для включения нерелизных зон.

## Как добавить готовую зону

1. Завершить её доработку и проверить редактор, расчёт, КП и сохранение заказа.
2. Добавить её идентификатор (`window` или `door`) в `RELEASE_ZONE_IDS`.
3. Выполнить проверку типов, тесты расчётов и политики зон, собрать релиз.
4. Проверить готовую сборку, затем опубликовать обновление обычным способом. Изменение списка само по себе не обновляет уже опубликованное приложение.

Идентификаторы зон не переименовывать. Код скрытых зон не удаляется; существующие заказы, PDF и кабинет менеджера не фильтруются этим списком.

## Проверки перед выпуском

- `pnpm --filter @workspace/bamboo-studio run typecheck`
- `pnpm --filter @workspace/bamboo-studio run test:calc`
- `pnpm --filter @workspace/bamboo-studio run test:zones`
- `pnpm --filter @workspace/bamboo-studio run build`
- В готовой сборке: четыре карточки, выбор каждой зоны, переход назад и сброс; оба типа ТВ и все формы колонны; расчёт КП и сохранение заказа.

Скрытие карточек не изолирует изменения общего редактора и не является механизмом авторизации. Если доработка окон или дверей затрагивает общую отрисовку, состояние поверхностей или расчёты, проверять также уже выпущенные зоны. Незавершённые изменения общего кода держать отдельно от стабильной версии (например, в отдельной ветке) и не включать в следующий релиз до проверки.
