# Проверка PDF между независимыми соединениями

Запуск из корня **среды разработки**:

```sh
pnpm test:pdf-integration
```

Это отдельная, явно запускаемая интеграционная проверка. Обычный `test` исключает
`*.integration.test.ts`: он не должен неожиданно создавать объекты App Storage.
Для интеграционной проверки необходимы работающие PostgreSQL среды разработки,
App Storage и локальная авторизация Replit sidecar. Отсутствие инфраструктуры —
ошибка запуска, а не успешный пропуск тестов. Не запускать в production.

## Изоляция

- Тест создаёт собственную случайную схему PostgreSQL. Выделенные соединения
  работают с `search_path`, содержащим только эту схему, без `public`.
- Привязка и очистка используют разные реальные соединения/транзакции.
  Номера backend PID и ожидающие advisory-lock записи проверяются через PostgreSQL.
- Объекты находятся только в случайном подкаталоге
  `integration-tests/pdf-lifecycle/<run-id>` внутри настроенного приватного
  каталога. Исходная настройка хранилища не меняется.
- Подмена адаптеров ограничивается маршрутизацией в тестовую схему/каталог,
  управляемым временем и барьерами. SQL, блокировки, чтение метаданных, поколения,
  копирование, HTTP PUT, скачивание и условное удаление настоящие.
- Очистка теста ограничена точными созданными объектами и проверкой префикса
  запуска. Она использует свежее поколение и `ifGenerationMatch`. Рабочие
  объекты и схемы не удаляются; ошибка уборки не считается успешным тестом.

Тест использует настоящую общую advisory-блокировку приложения в development.
На время коротких управляемых ожиданий она может задержать сохранение PDF или
фоновую очистку в этом окружении. Сроки запросов и ожиданий ограничены.

## Проверяемые гонки

1. Привязка уже скопировала PDF, но ещё не зафиксировала ссылку. Очистка с другого
   соединения должна ждать блокировку. После commit она повторно проверяет ссылку
   и сохраняет итоговый файл; менеджер скачивает исходные байты после очистки.
2. Привязка с ещё действующим разрешением ждёт работающую очистку. Разрешение
   истекает во время ожидания. После получения блокировки маршрут обязан заново
   проверить его и вернуть 403, не скопировав и не прикрепив PDF.
3. После настоящего чтения метаданных конкурентный подписанный PUT заменяет файл.
   Удаление старого поколения получает настоящий ответ 412 от хранилища.
   Обновлённый файл остаётся доступен с новым поколением и точными новыми байтами.

Для проверки 24-часового хранения не нужно ждать сутки или подделывать метаданные:
тест передаёт управляемое будущее время только проверке возраста в очистке.
Для срока разрешения меняется только `Date.now`; таймеры транспорта не подменяются.
